Nginx2Root 취약점 대응: 폐쇄망에서 Nginx 1.31.9 컴파일 설치

23 Nov 2026

Reading time ~5 minutes

Nginx2Root 취약점 대응, 폐쇄망에서 Nginx 컴파일 설치

예전에 Nginx source를 이용한 컴파일 설치를 정리한 적이 있습니다.

당시에는 서버에서 필요한 파일을 내려받고 컴파일하면 끝났습니다. 그런데 이번에는 상황이 다릅니다. 최근 Nginx2Root라는 이름으로 알려진 보안 취약점 때문에 Nginx 버전을 올려야 하는데, 운영 서버가 폐쇄망입니다.

Nginx 소스뿐 아니라 PCRE2, OpenSSL, zlib까지 외부망에서 준비해야 합니다. 파일 하나만 빠져도 다시 반입해야 하니 번거롭습니다.

그래서 필요한 소스를 한 번에 준비하고, 폐쇄망 서버에서는 Shell을 실행해 컴파일하도록 만들었습니다.

Nginx 공식 보안 공지와 소스 다운로드 주소를 확인해 정리했습니다. 다만 이 Shell로 실제 폐쇄망 운영 서버에서 컴파일하고 전환한 결과는 아직 없습니다. 운영 환경에 적용하기 전 별도 검증이 필요합니다.

Nginx2Root, 무엇을 패치해야 할까?

Nginx 공식 보안 공지에 올라온 최근 취약점 중 주요 항목입니다.

CVE 문제 공식 심각도
CVE-2026-123007 HTTP/2 흐름 제어 처리 중 메모리 손상 major
CVE-2026-118899 TLS 1.3 요청 본문 처리 중 무한 루프 major
CVE-2026-123633 HTTP/2 Use-after-free medium
CVE-2026-123634 Resolver 응답 처리 중 Use-after-free medium
CVE-2026-113425 Mail proxy 모듈 Use-after-free major

HTTP/3, PROXY protocol v2, stream 관련 보안 공지도 함께 확인할 필요가 있습니다. 실제 영향 여부는 사용하는 Nginx 버전, 컴파일 옵션, 운영 설정에 따라 달라질 수 있습니다.

이름에 Root가 들어간다고 모든 서버에서 곧바로 root 권한 탈취가 가능하다고 단정할 수는 없습니다. 실제 공격 조건과 영향은 개별 CVE 공지를 확인해야 합니다.

2026년 11월 23일 기준 Nginx 공식 패치 버전은 다음과 같습니다.

구분 패치 버전
Mainline 1.31.9 이상
Stable 1.30.7 이상

대부분의 최근 공지는 두 버전을 비취약 버전으로 표기합니다. 다만 CVE-2026-120993(PROXY protocol v2)의 공식 공지는 1.31.9 이상을 명시합니다.

이번에는 Mainline 1.31.9를 기준으로 준비했습니다.

1. 기존 Nginx 설치 상태 확인

먼저 현재 서버에서 실제로 실행 중인 Nginx를 확인해야 합니다.

command -v nginx
nginx -V 2>&1
ps -ef | grep '[n]ginx'
systemctl cat nginx

# 실제 실행 중인 master PID를 확인한 후
readlink -f /proc/<마스터_PID>/exe

PATH에 있는 Nginx와 systemd에서 사용하는 바이너리가 다를 수도 있습니다.

특히 nginx -V에 출력되는 configure arguments를 저장해 둡니다.

/usr/local/nginx/sbin/nginx -V > nginx-version-before.txt 2>&1

기존에 --conf-path, --user, --group, --add-module, --add-dynamic-module 등을 사용했다면 새 빌드에서도 확인해야 합니다.

이를 간단히 점검하기 위한 audit.sh도 준비했습니다.

./audit.sh /usr/local/nginx/sbin/nginx

2. 외부망에서 필요한 소스 준비

소스 버전
Nginx 1.31.9
PCRE2 10.49
OpenSSL 3.5.9
zlib 1.4

사용할 Shell은 세 개입니다.

  • prepare.sh: 인터넷이 되는 PC에서 소스 다운로드
  • install.sh: 폐쇄망 Linux 서버에서 컴파일 설치
  • audit.sh: 기존 Nginx 바이너리와 빌드 옵션 확인

셋을 같은 폴더에 두고 외부망에서 실행합니다.

chmod +x prepare.sh install.sh audit.sh
./prepare.sh

실행하면 다음과 같은 디렉토리가 만들어집니다.

nginx-offline-bundle/
├── audit.sh
├── install.sh
├── versions.env
└── sources/
    ├── nginx-1.31.9.tar.gz
    ├── nginx-1.31.9.tar.gz.asc
    ├── pcre2-10.49.tar.gz
    ├── openssl-3.5.9.tar.gz
    ├── zlib-1.4.tar.gz
    └── SHA256SUMS

SHA256SUMS는 다운로드한 파일의 체크섬입니다. 파일을 옮긴 뒤 변경 여부를 확인할 수 있습니다.

다만 스스로 계산한 체크섬은 원본 배포처의 진위를 보장하지 않습니다. Nginx는 공식 서명 파일인 .asc도 같이 내려받습니다. 공식 PGP 공개키의 지문을 신뢰할 수 있는 경로에서 확인한 다음 서명을 검증해야 합니다. PCRE2, OpenSSL, zlib도 배포처 서명이나 공식 체크섬을 별도로 확인해야 합니다.

3. 폐쇄망에서 컴파일 설치

준비한 디렉토리를 폐쇄망 서버로 가져옵니다.

서버에는 gcc, make, perl, tar 및 필요한 개발용 시스템 헤더가 설치되어 있어야 합니다. 이 Shell은 OS별 RPM/DEB 빌드 도구까지 내려받지는 않습니다.

예전 설치를 덮어쓰지 않도록 새로운 경로를 지정해 빌드합니다.

cd nginx-offline-bundle

sudo NGINX_USER=svm \
  NGINX_GROUP=svm \
  NGINX_PREFIX=/opt/nginx-1.31.9 \
  ./install.sh

svm 사용자와 그룹은 예시입니다. 서버에 실제로 존재하는 서비스 계정을 지정해야 합니다.

공식 서명 키를 검증해 준비한 경우 아래처럼 서명 검증도 수행할 수 있습니다.

sudo NGINX_TRUSTED_KEYRING=/secure/path/nginx-trusted.gpg \
  NGINX_USER=svm \
  NGINX_GROUP=svm \
  NGINX_PREFIX=/opt/nginx-1.31.9 \
  ./install.sh

설치 Shell은 압축 파일을 확인하고 아래 작업을 수행합니다.

  1. 소스 체크섬 확인 및 선택적 Nginx 서명 검증
  2. 압축 해제 및 ./configure 실행
  3. make, make install 실행
  4. nginx -V와 nginx -t로 새 설치 확인

컴파일할 때 사용하는 주요 옵션은 다음과 같습니다.

--with-pcre=/path/to/pcre2-10.49
--with-pcre-jit
--with-zlib=/path/to/zlib-1.4
--with-openssl=/path/to/openssl-3.5.9
--with-http_ssl_module
--with-http_v2_module
--with-http_sub_module

예전에 사용했던 sub_filter 기능도 포함했습니다.

주의: 제공한 Shell은 기본적인 Nginx 빌드용입니다. 기존 운영 서버가 stream, mail, HTTP/3, 서드파티 모듈, 별도의 경로 옵션 등을 사용한다면 이전 nginx -V 결과를 바탕으로 빌드 옵션을 추가해야 합니다. 동적 모듈은 새 버전에 맞춰 다시 빌드해야 할 수도 있습니다.

4. 새 바이너리 검증

/opt/nginx-1.31.9/sbin/nginx -V
/opt/nginx-1.31.9/sbin/nginx -t

여기서 -t가 성공해도 실제 운영 설정까지 검증한 것은 아닙니다. 신규 설치 디렉토리의 기본 설정을 검사했을 수 있습니다.

운영 서버의 설정 파일 경로를 확인한 뒤 새 바이너리로 다시 검사합니다.

/opt/nginx-1.31.9/sbin/nginx \
  -t -c /실제/운영/nginx.conf

기존 설정이 상대 경로를 사용한다면 -p 또는 컴파일 시 설정한 경로도 맞춰야 합니다. load_module로 불러오는 모듈 호환성도 확인합니다.

5. 중요한 것은 실제 운영 프로세스 교체

새 Nginx를 컴파일하고 설치해도 기존 서비스가 이전 바이너리로 실행 중이라면 패치가 끝난 것이 아닙니다.

운영 전환은 다음 순서로 진행하는 편이 안전합니다.

  1. 기존 바이너리, nginx.conf, conf.d, 인증서 경로, 동적 모듈 및 systemd unit 백업
  2. 기존과 새 빌드 옵션 비교, 누락된 모듈 확인
  3. 새 바이너리로 운영 설정 문법 검사
  4. 점검 시간에 서비스 시작 경로 또는 바이너리 교체
  5. 기존 실행 방식에 따라 서비스 재시작
  6. 새 마스터·워커 프로세스, 버전, 실제 HTTP/HTTPS 응답 확인

여기서는 기존 Nginx를 자동으로 덮어쓰거나 재시작하지 않도록 했습니다. 패키지 설치형인지 직접 컴파일한 버전인지에 따라 교체 방법이 다르기 때문입니다. 기존 시스템에 맞춘 전환 작업이 필요합니다.

서비스 교체 후에는 반드시 확인합니다.

ps -ef | grep '[n]ginx'
readlink -f /proc/<마스터_PID>/exe
/path/to/actual/nginx -V 2>&1

새 버전의 바이너리 파일이 있다고 끝난 것이 아닙니다. 실제 마스터와 워커가 새 버전으로 떠 있는지 확인해야 합니다. 롤백할 때도 바이너리뿐 아니라 변경한 설정과 모듈을 같이 되돌려야 합니다.

마무리

예전에 Nginx를 컴파일할 때는 필요한 소스를 받아 configure와 make만 실행했습니다. 폐쇄망에서는 준비할 파일이 늘어나고, 보안 패치라면 기존 서비스와의 호환성까지 확인해야 합니다.

이번에는 소스 다운로드와 컴파일을 Shell로 묶었습니다. 설치까지는 간단하게 만들었지만, 운영 중인 바이너리를 바꾸는 작업은 서버 환경에 맞게 진행하도록 남겨 두었습니다.

실제 폐쇄망에서 컴파일과 운영 전환까지 테스트한 후 발생한 오류와 해결 방법도 추가해 볼 생각입니다.
